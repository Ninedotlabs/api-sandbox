# MCP Server and Docs Page — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Let Claude drive every feature of Universal API — create projects, design resources, add endpoints, seed and edit records, run the AI generate/edit flows, and call the mock endpoints — through an MCP server, documented on the site.

**Architecture:** One module defines every tool (name, description, zod schema, handler). Two transports import it: a stdio bin for local use and a Streamable HTTP route for the deployed app. Handlers call `/api/v1` with a bearer token, so the MCP server has exactly the capabilities the management API has — no second data path, no privileged backdoor.

**Tech Stack:** `@modelcontextprotocol/sdk`, zod 4, Next.js route handler, Vitest.

**Spec:** `docs/superpowers/specs/2026-09-20-backend-and-mcp-design.md` §5–6

**Depends on:** Backend Phase 1 (the `/api/v1` management API). Do not start before it is merged.

## Global Constraints

- Tool definitions live in exactly one module. Both transports import it. A tool that exists in one transport and not the other is a defect.
- Every tool argument is validated with zod before any network call. Every handler returns compact JSON, never prose wrapped around JSON.
- `UNIVERSAL_API_TOKEN` is read from the environment, sent only as an `Authorization: Bearer` header, never logged and never echoed in a tool result. A tool result that would contain the token is a defect.
- Destructive tools (`delete_*`, `replace_records`) say in their description that the change takes effect immediately and that the result carries the undo payload.
- Tool names are verb-first and snake_case. Descriptions are one sentence, written for a model deciding whether to call the tool — what it does and when to use it, not how it is implemented.
- No emoji. Plain-language errors: a failed call returns the server's `error` string, not a stack trace.
- Before each commit: `npm test`, `npx tsc --noEmit`, `npm run lint`, `npm run build` clean.

## Task 1: Tool definitions and the API client

**Files:** `src/mcp/client.ts`, `src/mcp/tools.ts` (+ `src/mcp/tools.test.ts`)

**Produces:**
```ts
export interface McpTool<A extends z.ZodTypeAny = z.ZodTypeAny> {
  name: string; description: string; schema: A;
  handler(args: z.infer<A>, client: ApiClient): Promise<unknown>;
  destructive?: boolean;
}
export const TOOLS: McpTool[]
export function createApiClient(baseUrl: string, token: string): ApiClient
```

- `ApiClient` is a thin `fetch` wrapper: `get/post/patch/del(path, body?)`, sending the bearer token, parsing `{ data }` or throwing an `Error` carrying the server's `error` string.
- The tool list, matching spec §5: `list_projects`, `get_project`, `create_project`, `update_project`, `delete_project`, `duplicate_project`, `create_resource`, `update_resource`, `delete_resource`, `create_endpoints`, `update_endpoint`, `delete_endpoint`, `list_records`, `replace_records`, `add_record`, `delete_record`, `generate_api`, `edit_api`, `call_mock_endpoint`.
- `call_mock_endpoint` is the one that does not go through `/api/v1`: it issues a real request against `/{slug}/{path}` so Claude can exercise a mock API the way a client would.
- Tests: every tool has a unique name; every schema rejects a missing required argument; each handler calls the expected method and path against a mocked `ApiClient` and returns its `data`; a handler whose API call fails surfaces the server's error string unchanged.

## Task 2: stdio transport

**Files:** `src/mcp/stdio.ts`, `package.json` (bin entry, build script) (+ test)

- Reads `UNIVERSAL_API_URL` (default `http://localhost:3000`) and `UNIVERSAL_API_TOKEN` from the environment. If the token is missing, exit with a message naming the variable — never start unauthenticated.
- Registers every tool from `TOOLS` on an `McpServer` over `StdioServerTransport`.
- Build to a runnable file so `claude mcp add universal-api -- node ./dist/mcp/stdio.js` works.
- Test: the registered tool names equal `TOOLS.map(t => t.name)`.

---

## Task 3: HTTP transport

**Files:** `src/app/api/mcp/route.ts` (+ test)

- Streamable HTTP transport at `/api/mcp`, `runtime = "nodejs"`.
- Requires `Authorization: Bearer <UNIVERSAL_API_TOKEN>` on every request, compared with `crypto.timingSafeEqual`; 401 with a plain-language message otherwise. Unlike `/api/v1`, there is **no same-origin exemption** — a browser reaching this endpoint without a token is not a case we want to allow.
- Registers the same `TOOLS`.
- Tests: no token → 401; valid token → the tool list matches `TOOLS`; the exposed list is identical to the stdio transport's.

## Task 4: `/mcp` docs page

**Files:** `src/app/mcp/page.tsx`, `src/components/mcp/*` (+ tests)

- Built in the existing visual system (light theme, indigo accent, `CodePanel` for snippets, `Kicker` headings). No new design vocabulary.
- Sections:
  1. **Connect** — copy-paste `claude mcp add` command for local stdio, and the JSON block for Claude Desktop's config. A tab switches between local and deployed (HTTP) setup.
  2. **Token** — the token masked (`ua_••••••••1234`) with a copy button, fetched from a server component so the full value never sits in the page source for someone who should not have it.
  3. **Tools** — a table generated from `TOOLS` at build time: name, description, arguments with types, and whether it is destructive. Because it is generated, the docs cannot describe a tool that does not exist.
  4. **What to ask** — worked examples in plain English, e.g. "add a Reviews resource to my Bookshop API with rating and comment, then give it 10 sample rows", "duplicate my Store API and rename the copy to Staging".
- A short, honest note that while sign-in is deferred, anyone holding the token can modify every project.
- Tests: the rendered tool table has one row per entry in `TOOLS`; the token is never rendered in full.

## Task 5: End-to-end verification

**Files:** `src/mcp/e2e.test.ts` (+ README/AGENTS.md updates)

- Against a live dev server and a real database: create a project, add a resource with fields, generate its CRUD endpoints, seed records, call a mock endpoint through `call_mock_endpoint` and assert the seeded data comes back, then delete the project and assert it is gone.
- Skips cleanly when `DATABASE_URL` or a running server is absent, so CI stays green.
- Document in `AGENTS.md`: how to run the MCP server locally, how to point it at a deployed instance, and how to rotate the token.
